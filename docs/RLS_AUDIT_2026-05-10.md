```sql

-- List all RPCs SECURITY DEFINER

FROM pg_proc
WHERE pronamespace = 'public'::regnamespace
```

### Overall risk level

🔴 **P0 — BLOCKING for Mosimann (5 critical risks)**

1. **Complete drift between RLS and frontend.** All write policies rely on `user_roles` + `has_any_workspace_role(...)`. The frontend (`RoleContext.tsx:167-186`) and `update_workspace_member` read/write exclusively `workspace_members.access_level`. Consequence: if Mosimann invites a new member through the current flow, their `access_level` is set but **no `user_roles` entry is created** → all RLS-protected writes will be rejected by Postgres. Symptom in UI: "permission denied for table tracks", upload failing silently, etc.

2. **`track_documents` has no access_level check.** The current policies (`001_track_documents.sql:40-57`) allow **any `is_workspace_member`** to `INSERT` / `UPDATE` / `SELECT`. A Viewer can therefore upload, modify, and delete contracts. For a premium artist sharing split sheets or riders with labels, this is unacceptable.

3. **Storage bucket `documents` is fully open.** The storage policies (`001_track_documents.sql:64-74`) allow `bucket_id = 'documents'` without checking the path → **every authenticated user, regardless of workspace, can read/write/delete any document**. Risk of cross-workspace leaks.

4. **`notifications` INSERT is too permissive.** The "System can create notifications" policy (`125248_*.sql:309`) checks `is_workspace_member(auth.uid(), workspace_id)` but **not the target `user_id`**. Consequence: a workspace Viewer can spam another member's notifications, even inject phishing links.

5. **Public pages with anonymous writes — non-versioned policies.** `SharedStemAccess.tsx`, `SignAgreement.tsx`, `StudioSession.tsx` make `INSERT`/`UPDATE` with an anon client on `track_comments`, `signature_requests`, `studio_submissions`. **No anon write policy for these tables is in the repo** (only `track_comments` has an anon insert/select policy in `20260315_shared_link_anon_rls.sql`, but not the UPDATE). If production has overly permissive or nonexistent policies, an attacker can forge signatures, submit fakes to the studio, or corrupt comments.

🟡 **P1 — TO FIX THIS WEEK (4 risks)**

6. **`audit_logs` SELECT without workspace filtering on the frontend** (`TeamContext.tsx:183`) — RLS must scope by `workspace_id`. If the policy in production scopes by `user_id`, it works by luck; but we don't know without checking.
7. **Tables `catalog_shares`, `invitations`, `link_events` are non-versioned** — probably in production, but their policies are opaque. `catalog_shares` is critical because it defines who sees what between workspaces.
8. **Helper `has_workspace_access_level(_min_level)` is missing** — the hierarchy viewer < pitcher < editor < admin must be expressible simply in SQL to avoid manual arrays in every policy.
9. **`handle_new_user` trigger** inserts into `user_roles` (legacy) but not into `workspace_members.access_level`. And `RoleContext.tsx` only reads `access_level`. To verify that the default `viewer` on the frontend masks the bug.

🟢 **P2 — NICE TO HAVE**

10. Rename policies for consistency (`"Members can view tracks"` → `"tracks_select_members"`, etc.).
11. Composite index on `workspace_members(workspace_id, user_id, access_level)` to speed up RLS checks.
12. Document in `docs/AUTH_PATTERNS.md` that `user_roles` is definitively legacy.

## Concrete risks — examples

### Scenario 1 — Mosimann invites his sound engineer as Editor (P0)

1. Mosimann (admin) opens the Team panel → invites Karim with `access_level = 'editor'`, `professional_title = 'Mix Engineer'`.
2. Karim accepts the invitation → entry created in `workspace_members` with `access_level = 'editor'`. **No `user_roles` entry.**
3. Karim tries to upload a new mix → `INSERT INTO tracks` → RLS check `has_any_workspace_role(auth.uid(), workspace_id, [...])` → **FALSE** → "new row violates row-level security policy".
4. Karim sees "Upload failed" without details. Frustrated, he gives up.

**Fix:** migrate all policies to `has_workspace_access_level('pitcher')` or higher.

### Scenario 2 — Viewer replaces a contract (P0)

1. Mosimann adds his manager Théo as `access_level = 'viewer'` so he can listen to demos and give his opinion.
2. Théo sees that a draft of "split sheet" is uploaded on the track "Lune" → policy `Workspace members can update documents` → **SUCCEEDS**.
3. Théo uploads a malicious PDF in place of the original contract → success.
4. Mosimann signs without re-reading the diff → legal drama.

**Fix:** `track_documents` UPDATE/INSERT → `access_level >= 'editor'`. DELETE → uploader OR admin.

### Scenario 3 — Cross-workspace doc leak (P0)

1. A user from label A is a member of workspace A.
2. He knows the Supabase storage URL pattern: `documents/{workspace_id}/{file}`.
3. He guesses or finds the `workspace_id` of label B → does `supabase.storage.from('documents').download(path)` → storage policy `bucket_id = 'documents'` → **SUCCEEDS**.
4. Leak of all documents from label B.

**Fix:** policy scope on the path `(storage.foldername(name))[1]::uuid IN (SELECT workspace_id FROM workspace_members WHERE user_id = auth.uid())`.

### Scenario 4 — Notification spam (P0)

1. A Workspace Viewer does `supabase.from('notifications').insert({ workspace_id, user_id: <admin_uid>, kind: 'phishing', payload: { url: 'evil.com' } })`.
2. Policy "System can create notifications" → `is_workspace_member(auth.uid(), workspace_id)` → **SUCCEEDS**.
3. The admin receives the notification → clicks the link.

**Fix:** remove the public INSERT policy, create a RPC `create_notification` that validates the actor and context.

## Frontend code impact after applying the fixes

No frontend code changes are required to apply the SQL — all RPCs on the frontend will continue to work. **The changes are 100% transparent as long as**:

- Writes already go through the documented RPCs SECURITY DEFINER (verified — all critical writes do).
- SELECTs via `.from('TABLE')` go through RLS, which becomes more permissive in the new version (anyone with adequate `access_level` can read what they could read before).

### Manual tests to perform after application

1. **Owner workflow**: create a workspace → upload a track → edit it → delete it → everything should work (admin auto via `workspace.owner_id = user.id`).
2. **Invited admin**: invite a collaborator as `admin` → they can do everything except delete workspace.
3. **Editor**: invite as `editor` → they can upload, edit all tracks, edit stems, edit lyrics. They cannot delete tracks, modify splits, invite members.
4. **Pitcher**: invite as `pitcher` → they can upload, create playlists, create pitches, create shared links, edit own tracks. They cannot edit other tracks or delete.
5. **Viewer**: invite as `viewer` → they can only read/listen. All INSERT/UPDATE/DELETE rejected.
6. **Incoming catalog share**: a third-party workspace shares a track → it appears in Mosimann's catalog (via RPC `get_shared_workspace_tracks`).
7. **Public shared link**: create a shared link → open the URL in a private non-connected browser → listen to the track → leave a comment → everything should work.
8. **Sign agreement**: generate a signature_request → open the signed URL → sign → status becomes "signed". (Verify that the anon UPDATE is scoped on the token only.)
9. **Studio QR**: open a studio session → submit a collaborator track → the admin receives the notification → accepts the submission.
10. **Storage documents**: an Editor uploads a contract → a Viewer cannot replace it but can download it.

### Known regression risks

- **`Creators can delete own shared links`** is removed in the fix. If a Pitcher was used to directly delete their own links (not via UPDATE `disabled`), the button will no longer work on the UI. The frontend already uses UPDATE for disabled (`SharedLinksContext.tsx`), so this case is unlikely.
- **`notifications` INSERT** becomes self-only. If somewhere in the code notifications are created for another user via `.from('notifications').insert(...)` (not via RPC), it will break. **To verify in the frontend** before execution.

The SQL fix is in `supabase/migrations/rls_audit_fixes.sql`. Read it **completely** before executing, then run it block by block in the Supabase SQL Editor.
