## ⚠️ Limitation importante

Cet audit a été conduit **uniquement à partir du code versionné** dans le repo. Plusieurs tables et RPCs sont référencées par le frontend mais **n'apparaissent pas dans les migrations SQL** (très probablement créées via Supabase Studio sans migration committée). Pour ces tables, l'audit ne peut que **lister les hypothèses** et **demander une vérification manuelle** dans le SQL Editor Supabase via :

```sql
-- Lister toutes les policies de production
SELECT schemaname, tablename, policyname, cmd, qual, with_check
FROM pg_policies WHERE schemaname = 'public'
ORDER BY tablename, policyname;

-- Lister toutes les RPCs SECURITY DEFINER
SELECT proname, pg_get_function_arguments(oid), pg_get_functiondef(oid)
FROM pg_proc
WHERE pronamespace = 'public'::regnamespace
  AND prosecdef = true
ORDER BY proname;
```

### Niveau de risque global

🔴 **P0 — BLOQUANT pour Mosimann (5 risques critiques)**

1. **Drift complet entre RLS et frontend.** Toutes les policies de write s'appuient sur `user_roles` + `has_any_workspace_role(...)`. Le frontend (`RoleContext.tsx:167-186`) et `update_workspace_member` lisent/écrivent exclusivement `workspace_members.access_level`. Conséquence : si Mosimann invite un nouveau membre via le flow actuel, son `access_level` est défini mais **aucune entrée `user_roles` n'est créée** → toutes les writes RLS-protégées seront refusées par Postgres. Symptôme côté UI : "permission denied for table tracks", upload qui échoue silencieusement, etc.

2. **`track_documents` n'a aucun check de access_level.** Les policies actuelles (`001_track_documents.sql:40-57`) autorisent **n'importe quel `is_workspace_member`** à `INSERT` / `UPDATE` / `SELECT`. Un Viewer peut donc uploader, modifier et supprimer des contrats. Pour un artiste premium qui partage des splits sheets ou des riders avec des labels, c'est inacceptable.

3. **Storage bucket `documents` totalement ouvert.** Les policies storage (`001_track_documents.sql:64-74`) autorisent `bucket_id = 'documents'` sans vérifier le path → **tout utilisateur authentifié, peu importe son workspace, peut lire/écrire/supprimer n'importe quel document**. Risque de fuite croisée entre catalogues.

4. **`notifications` INSERT trop permissive.** La policy "System can create notifications" (`125248_*.sql:309`) vérifie `is_workspace_member(auth.uid(), workspace_id)` mais **pas le `user_id` cible**. Conséquence : un Viewer du workspace peut spammer les notifications d'un autre membre, voire injecter des liens phishing.

5. **Pages publiques avec writes anonymes — policies non versionnées.** `SharedStemAccess.tsx`, `SignAgreement.tsx`, `StudioSession.tsx` font des `INSERT`/`UPDATE` avec un client anon sur `track_comments`, `signature_requests`, `studio_submissions`. **Aucune policy de write anon pour ces tables n'est dans le repo** (seul `track_comments` a une policy anon insert/select dans `20260315_shared_link_anon_rls.sql`, mais pas l'UPDATE). Si la prod a des policies trop permissives ou inexistantes, un attaquant peut forger des signatures, soumettre des fakes au studio, ou pourrir les commentaires.

🟡 **P1 — À FIXER CETTE SEMAINE (4 risques)**

6. **`audit_logs` SELECT sans filtre workspace côté frontend** (`TeamContext.tsx:183`) — RLS doit obligatoirement scoper par `workspace_id`. Si la policy en prod scope par `user_id`, ça marche par chance ; mais on ne le sait pas sans vérifier.
7. **Tables `catalog_shares`, `invitations`, `link_events` non versionnées** — probablement en prod, mais leurs policies sont opaques. `catalog_shares` est critique car il définit qui voit quoi entre workspaces.
8. **Helper `has_workspace_access_level(_min_level)` manquant** — la hiérarchie viewer < pitcher < editor < admin doit être exprimable simplement en SQL pour éviter des arrays manuels dans chaque policy.
9. **`handle_new_user` trigger** insère dans `user_roles` (legacy) mais pas dans `workspace_members.access_level`. Or `RoleContext.tsx` ne lit que `access_level`. À vérifier que le default `viewer` côté frontend masque le bug.

🟢 **P2 — NICE TO HAVE**

10. Renommer les policies pour cohérence (`"Members can view tracks"` → `"tracks_select_members"`, etc.).
11. Index composite sur `workspace_members(workspace_id, user_id, access_level)` pour accélérer les checks RLS.
12. Documenter dans `docs/AUTH_PATTERNS.md` que `user_roles` est définitivement legacy.

## Risques concrets — exemples

### Scénario 1 — Mosimann invite son ingé son comme Editor (P0)

1. Mosimann (admin) ouvre le panel Team → invite Karim avec `access_level = 'editor'`, `professional_title = 'Mix Engineer'`.
2. Karim accepte l'invitation → entrée créée dans `workspace_members` avec `access_level = 'editor'`. **Aucune entrée `user_roles`.**
3. Karim essaie d'uploader un nouveau mix → `INSERT INTO tracks` → RLS check `has_any_workspace_role(auth.uid(), workspace_id, [...])` → **FALSE** → "new row violates row-level security policy".
4. Karim voit "Upload failed" sans détail. Frustré, il abandonne.

**Fix :** migrer toutes les policies vers `has_workspace_access_level('pitcher')` ou supérieur.

### Scénario 2 — Viewer remplace un contrat (P0)

1. Mosimann ajoute son manager Théo comme `access_level = 'viewer'` pour qu'il puisse écouter les démos et donner son avis.
2. Théo voit qu'un draft de "split sheet" est uploadé sur le track "Lune" → policy `Workspace members can update documents` → **PASSE**.
3. Théo upload un PDF malveillant à la place du contrat original → succès.
4. Mosimann signe sans relire le diff → drama légal.

**Fix :** `track_documents` UPDATE/INSERT → `access_level >= 'editor'`. DELETE → uploader OR admin.

### Scénario 3 — Cross-workspace doc leak (P0)

1. Un user de label A est membre de workspace A.
2. Il connaît l'URL pattern Supabase storage : `documents/{workspace_id}/{file}`.
3. Il devine ou trouve le `workspace_id` du label B → fait `supabase.storage.from('documents').download(path)` → policy storage `bucket_id = 'documents'` → **PASSE**.
4. Fuite de tous les documents du label B.

**Fix :** policy storage scope sur le path `(storage.foldername(name))[1]::uuid IN (SELECT workspace_id FROM workspace_members WHERE user_id = auth.uid())`.

### Scénario 4 — Spam notifications (P0)

1. Un Viewer du workspace fait `supabase.from('notifications').insert({ workspace_id, user_id: <admin_uid>, kind: 'phishing', payload: { url: 'evil.com' } })`.
2. Policy "System can create notifications" → `is_workspace_member(auth.uid(), workspace_id)` → **PASSE**.
3. L'admin reçoit la notif → clique sur le lien.

**Fix :** retirer la policy publique INSERT, créer une RPC `create_notification` qui valide l'acteur et le contexte.

## Recommandations classées

### P0 — Bloquants pour Mosimann (avant launch)

1. **Migrer toutes les policies de write vers `access_level`** (helper `has_workspace_access_level`).
2. **Durcir `track_documents`** (INSERT/UPDATE → editor+).

## Impact code frontend après application des fixes

Aucune modification de code frontend n'est requise pour appliquer le SQL — toutes les RPCs côté frontend continueront de fonctionner. **Les changements sont 100% transparents tant que** :

- Les writes passent déjà par les RPCs SECURITY DEFINER documentées (vérifié — tous les writes critiques le font).
- Les SELECT via `.from('TABLE')` passent par RLS, qui devient plus permissive dans la nouvelle version (toute personne avec `access_level` adéquat peut lire ce qu'elle pouvait lire avant).

### Tests manuels à effectuer après application

1. **Owner workflow** : créer un workspace → uploader un track → l'éditer → le supprimer → tout doit marcher (admin auto via `workspace.owner_id = user.id`).
2. **Admin invité** : inviter un collaborateur en `admin` → il peut tout faire sauf delete workspace.
3. **Editor** : inviter en `editor` → il peut upload, edit all tracks, edit stems, edit lyrics. Il ne peut pas delete tracks, modifier splits, inviter membres.
4. **Pitcher** : inviter en `pitcher` → il peut upload, créer playlists, créer pitches, créer shared links, edit own tracks. Il ne peut pas edit other tracks ni delete.
5. **Viewer** : inviter en `viewer` → il peut lire/écouter uniquement. Tout INSERT/UPDATE/DELETE refusé.
6. **Catalog share entrant** : un workspace tiers partage un track → il apparaît dans le catalogue de Mosimann (via RPC `get_shared_workspace_tracks`).
7. **Shared link public** : créer un shared link → ouvrir l'URL en navigation privée non connectée → écouter le track → laisser un commentaire → tout doit marcher.
8. **Sign agreement** : générer un signature_request → ouvrir l'URL signée → signer → status passe à "signed". (À vérifier que l'UPDATE anon est scoped sur le token uniquement.)
9. **Studio QR** : ouvrir une session studio → soumettre un track collaborateur → l'admin reçoit la notif → accepte la soumission.
10. **Storage documents** : un Editor upload un contrat → un Viewer ne peut pas le remplacer mais peut le télécharger.

### Risques de régression connus

- **`Creators can delete own shared links`** est supprimée dans le fix. Si un Pitcher avait l'habitude de delete ses propres liens directement (pas via UPDATE `disabled`), le bouton ne marchera plus côté UI. Le frontend utilise déjà l'UPDATE pour disabled (`SharedLinksContext.tsx`), donc cas peu probable.
- **`notifications` INSERT** devient self-only. Si un endroit du code crée des notifications pour un autre user via `.from('notifications').insert(...)` (pas via RPC), il cassera. **À vérifier dans le frontend** avant exécution.
